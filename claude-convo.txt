❯ I don't know if this is "spec compliant" or not, but Terminal.app and a
  pre-1.0 Ghostty used to have this nice behavior (that was leveraged by the
  delta diff tool) where if you set a background color and then cleared to the
  end of the line (or something close to that), then you'd get the background
  color applied to the full line no matter the terminal width. like, if you
  grew the terminal width, the background color would extend, and if you shrank
  the terminal width (so it's narrower than when delta produced its output) it
  would get trimmed nicely. so it's like the background color didn't have a
  width, it was like it was a property of the line.

  currently ghostty does not have this behavior: from the user's perspective,
  it seems to ignore this nice property that delta tries to achieve with the
  escape codes it emits, and instead seemingly assigns a background color per
  cell rather than per line, and does not extend or trim. this results in
  background colors wrapping in an unpleasant way.

  another claude looked into it and claimed this:

  - Ghostty's old terminal code handled this case on purpose.
  trimRowForResizeLessCols (979dc5a43, 2023-03-01) dropped trailing cells that
  had style but no character once they fell past the new width, with the
  comment "this is just an empty-character stylized cell, then we trim it".
  That clip-instead-of-wrap behavior is what you remember, and it matches
  Terminal.app.
    > - The terminal rewrite added isEmpty() with background cells counted as
  content (1d3057750, 2024-02-27). The current trimming logic arrived in
  8589f2c0f (2024-07-08). The old implementation, trimming included, was
  deleted in a416d4236 (2024-03-26).

⏺ Ghostty soft-wraps those background-only cells because of a narrow regression.
  I found it, wrote a test that fails, and made a small fix that passes. There
  are three commits on top of main, and the full libghostty-vt test suite
  passes.

  1. Where the code is

  The erase (CSI K) with a background color set. delta paints a line as
  ESC[48;…m, then the text, then ESC[0K. Erasing fills the cells with
  Screen.blankCell() → Style.bgCell() (src/terminal/style.zig:230). That
  produces cells tagged .bg_color_palette or .bg_color_rgb: a background color
  and no text.

  The resize. Changing the column count reflows every row through
  ReflowCursor.reflowRow (src/terminal/PageList.zig:1654). Before copying a row
  it trims trailing blank cells, and it decides what's blank with Cell.isEmpty()
  (src/terminal/page.zig:2351). That function counts background-only cells as
  content. That's correct for its other callers, such as scroll-clear and
  trailing-blank-row trimming.

  What goes wrong. A painted 10-column line keeps its full width of 10 cells.
  Shrink to 5 columns and the reflow soft-wraps the leftover 5 colored cells
  onto a new row, so one painted line becomes two. Growing never extends the
  color: the new columns are just empty.

  3. The fix (commit tznmlu)

  The change is three small edits in reflowRow:

  1. Find where the fill starts. For a row that isn't soft-wrapped, scan
     backward over trailing background-only cells to find fill_start. A
     soft-wrapped row is followed by more text, so all of its cells matter and
     nothing is trimmed.
  2. Keep tracked positions safe. Raise fill_start past any tracked position on
     the row, including the cursor. The existing code already does the same
     thing to cols_len two lines above. This guarantees every tracked position
     gets remapped and none is left pointing into a freed page.
  3. Don't wrap just for fill. When the reflow is about to soft-wrap and only
     fill cells remain (x >= fill_start), stop. Fill cells that still fit on the
     current row are kept.

  After the stop, the reflow is in exactly the state it's in when a row's text
  fills the new width exactly, which is an existing, well-tested path.

  I deliberately didn't port the old code literally (trim cells whose index is
  past the new width). That rule only works for a row that starts at column 0.
  It still wraps the fill on the last row of a long, soft-wrapped line, which
  one of the new tests covers.

  Two limits to mention in the report:
  - Narrower than the old code. It only trims erase-produced background cells.
    Old Ghostty also trimmed styled spaces, but spaces are real text a program
    wrote, so I left them alone.
  - Lossy, like the old code. Shrinking and then growing back doesn't bring the
    trimmed color back.

  5. Should it be fixed?

  There's no spec. One maintainer has written down how Ghostty breaks ties:
  spec, then kitty, then xterm, then common practice (#12497
  (https://github.com/ghostty-org/ghostty/discussions/12497)). The strongest
  argument for the report is that this was intentional behavior, with a test,
  that got lost in the rewrite.

  Ask only for the trimming. Asking for extend-on-grow means asking the
  maintainer to undo a deliberate 2023 decision, and the reason isn't public.

  I haven't checked what other terminals do today. Before filing, it's worth
  running printf '\e[41mfoo\e[K\e[0m\n' in Terminal.app, kitty and iTerm2, then
  narrowing each window and seeing whether the red wraps. A maintainer
  reportedly said xterm.js trims these cells too; I didn't verify that.

  A correction about delta: its help text says line-fill-method only applies in
  side-by-side mode. Unified diffs always use the erase, so this affects
  everyone using delta's default unified view.
